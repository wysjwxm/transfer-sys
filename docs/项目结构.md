# 转账系统 · 项目结构文档

> 行内转账（分库分片 + TCC 跨库）的可跑样例，兼作支付系统面试与 Spring 原理的练手载体。
> 设计口径、里程碑进度见 `src/main/resources/TODO.md`；本文件只讲「代码怎么摆、为什么这么摆、请求怎么走」。

| 项 | 取值 | 说明 |
|---|---|---|
| JDK | **1.8**（本机唯一） | 决定了 Spring Boot 版本上限 |

## 2. 运行形态：双实例分库（微服务）

**一份代码、两个进程、各连一个库**，不是单进程多数据源：

- 分片契约 `shardOf(userId) = userId % 2`。每实例退回**单数据源** → `@Transactional` 照常可用；
  分布式从"多数据源路由"退化成**跨进程 HTTP**。
- 账户按奇偶归位：`node0` 偶数(user 2、4)、`node1` 奇数(user 1、3)，端口 8080 / 8081，`peer-url` 互指。
- **协调者 = 转出方所在节点**。API 打错节点不自动转发，返回 `WRONG_NODE(1006)` 指引。
- 节点间 TCC 走内网接口 `POST /internal/tcc/try|confirm|cancel`（每个节点都既是 API host 又是 TCC 参与者）。
- 同分库转账 = 本地事务强一致；跨分库 = TCC（协调者 + 参与者）。应用层一行 `shardOf(from)==shardOf(to)` 分流。

```
                ┌─────────── node0 (8080, 偶数账户) ───────────┐
   用户 → node0 │ transfer_log(txn) · tcc_branch · /internal  │──HTTP─┐
                └─────────────────────────────────────────────┘        │ peer
                ┌─────────── node1 (8081, 奇数账户) ───────────┐        │
   用户 → node1 │ transfer_log(txn) · tcc_branch · /internal  │◀─HTTP──┘
                └─────────────────────────────────────────────┘
   跨片：发起方节点把"收款方分支"(PAYEE) 用 RestTemplate 打到对端 /internal/tcc/*
```

## 3. 分层架构：DDD 四层（含出站端口）

依赖方向**由外向内单向**：`interfaces → application → domain`，`infrastructure` 适配向内实现。

- **domain（领域层）**：只依赖自身与 JDK，不 import 任何 Spring/MyBatis 类型——分层核心裁判。
- **infrastructure（基础设施层）**：两类适配器，方向都向内：
  - 持久化适配器：实现 **domain** 的 Repository 接口；
  - 出站 HTTP 适配器 `HttpTccPeer`：实现 **application** 声明的端口 `TccPeer`（跨节点是"外部系统"）。
- **application（应用层）**：编排领域对象 + 划事务边界 + 声明 outbound 端口，不含业务规则。
- **interfaces（接口层）**：HTTP 形态转换，只粘合不决策。

```
                    ┌──────────────────────────────────────────────┐
  外            →   │ interfaces  Transfer/Account/InternalTcc + DTO│
                    └──────────────────────┬───────────────────────┘
                                           │ 调用（传 Command，收 Result）
                    ┌──────────────────────▼───────────────────────┐
                    │ application                                  │
                    │  TransferAppService(协调者,不开事务)           │
                    │  Recorder / LocalRunner / Participant  ←小事务│
                    │  端口接口 TccPeer   (+ PeerCallException)     │
                    └───────┬──────────────────────────┬───────────┘
                            │                          │
                 ┌──────────▼──────────┐      ┌────────▼──────────────┐
                 │ domain（规则/聚合）    │      │ infrastructure       │
                 │ Account(frozen)     │      │ persistence/*Impl    │
                 │ TransferService     │◄─────│   └ mybatis Mapper+XML│
                 │ Branch/Log 实体与状态 │      │ config/ShardProperties│
                 │ Repository 接口      │      │ peer/HttpTccPeer  ──实现──→ application.TccPeer
                 │ BizException/ErrorCode│      │                      │
                 └─────────────────────┘      └──────────────────────┘
```

## 5. 数据表（每节点同一份 schema.sql）

| 表 | 角色 | 关键列 / 约束 | 语义要点 |
|---|---|---|---|
| `account` | 本片账户 | `balance` + `frozen_amount` | 不变式：总资产 = balance + frozen；同片转账 frozen 恒 0 |
| `transfer_log` | **协调/回执记录**，只写在发起方节点 | `txn_no` UNIQUE、`request_no` UNIQUE、`status`(TRYING…)、`remark` | 受理即落 TRYING（失败也留痕）；终态见下 |
| `tcc_branch` | 本侧分支状态机（收方节点只留它） | `txn_no` UNIQUE、`role`(PAYER/PAYEE)、`status`(TRYED/CONFIRMED/CANCELLED) | 用条件更新实现 幂等 / 空回滚 / 悬挂 |

**transfer_log 终态判别口径**（面试要点）：

| 场景 | 是否发生过冻结 | 终态 |
|---|---|---|
| 同片失败（余额不足/自转/收款不存在/金额非法） | 否 | `FAILED` |
| 跨片付款方冻结前失败 | 否 | `FAILED` |
| 跨片收款方 Try 失败（付款方已冻又解冻） | 是 | `CANCELLED` |
| 确认阶段网络不确定 | 冻结/扣款进行中 | `CONFIRMING`（遗留，下期恢复/对账） |

## 6. 一次转账的调用链

### 同片（node1 上 1→3，强一致）
```
POST /api/v1/transfers → TransferAppService
  ① 归属守卫 shardOf(from)==node-id，否则 WRONG_NODE(1006)
  ② recordStarted(小事务)：插 TRYING；request_no 已存在 → 回原 txn_no 幂等结束
  ③ shardOf(from)==shardOf(to) → 同片分支
     LocalTransferRunner(@Transactional)：FOR UPDATE 升序锁 → TransferService 扣加
     → 落两账户 → transfer_log 置 SUCCESS     （同一事务）
  ④ 失败：事务回滚 → 另起小事务置 FAILED(remark=原因) → 抛回
```

### 跨片（node1 发起 1→2，协调者在付款方节点）
```
① 守卫 + recordStarted(TRYING)
② Phase1 Try 付款方(本地 TccParticipantService.PAYER) 先冻结 balance→frozen
     └ 失败(余额不足等) → FAILED（没冻过）
③ Phase2 Try 收款方(远程 /internal/tcc/try, role=PAYEE)：收方只登记不冻结
     └ 被拒/网络失败 → Cancel 本地付款方解冻 → CANCELLED → 抛对端错误码
④ Phase3 Confirm：本地付款方真扣 → 远程收款方入账
     └ 确认网络不确定 → CONFIRMING 遗留
⑤ 两侧都成功 → transfer_log 置 SUCCESS
```
- 收方"空 Try/Cancel"：收款方入账不会失败，所以 Try 不冻结——这是 TCC 设计里值得讲的点。
- 幂等/空回滚/悬挂全由 `tcc_branch` 单行状态机 + 条件更新承载（见 `TccParticipantService` 注释）。

## 7. 关键设计决策速查

| 决策 | 落点 | 备注 |
|---|---|---|
| 分库拓扑 | 双实例各连一库，`shardOf=userId%2` | 每实例单数据源，@Transactional 复活 |
| 分布式一致性 | 跨片 TCC，收方空 Try/Confirm | 同片仍本地强一致 |
| 协调者 | 转出方节点，API 打错返回 1006 | 不自动转发 |
| 协调记录 | transfer_log 只在发起方写 | 收方只留 tcc_branch |
| 失败留痕 | 受理即 TRYING，终态 FAILED/CANCELLED 区分 | 以"是否发生过冻结"判定 |
| 阶段幂等 | tcc_branch `TRYED→CONFIRMED/CANCELLED` 条件更新 | 空回滚插 CANCELLED、悬挂拒 Try |
| 事务归属 | 协调者无事务；小事务收敛到 Recorder/Runner/Participant | 防自调用绕代理 + 失败行可留痕 |
| request_no 幂等 | recordStarted 判重 + 唯一约束兜底 | 同号回原 txn_no，只动一次账 |

## 8. 测试与配置：一个必须知道的坑

- 自动化测试**不启真 HTTP**：
  - 同片：MockMvc 全链路打节点1（`@SpringBootTest`+`@ActiveProfiles("test")`），9 例覆盖成功/各类 FAILED/打错节点/幂等/参与者三阶段；
  - 跨片：`@MockBean TccPeer` 假扮收款节点，服务级验证 SUCCESS/CANCELLED/CONFIRMING 与 PAYEE 角色调用，4 例；
  - 每个套件**独立内存库名**（node1 / cross），类级 `@Transactional` 每例回滚互不污染。
- 真实双节点 HTTP（两实例互调 + 对端真实入账）由**冒烟 curl** 覆盖（见 TODO/验证清单），自动化双上下文留作下一步可选。
- 数据源隔离靠 **profile 覆盖**，不是同名文件覆盖。

> ⚠️ **坑（曾踩）**：在 `src/test/resources` 放**同名** `application.yml` 会把主配置整个遮蔽
> （test-classes 排在 classpath 前面，只解析第一个同名文件），`mybatis.mapper-locations` 丢失
> → XML 不加载 → `BindingException`。结论：跨环境叠加用 `application-{profile}.yml`，不要同名覆盖。
> 另：`clean` 会清掉 `target` 里孤儿编译产物，换测试类后记得 `mvn clean test`。

## 10. 一句话定位各关键类（面试口径）

- **`TransferService` 是领域规则，`TransferAppService` 是（分布式）事务编排**——协调者自身不开事务。
- **为什么事务要拆三个协作 bean**：自调用绕代理（@Transactional 失效）+ 失败行需留在独立已提交小事务里（审计）。
- **`Account.freeze/confirmFreeze/unfreeze` = TCC 的三态账务原语**；同片走 `withdraw/deposit`，frozen 恒 0。
- **`tcc_branch` 一行状态机回答 TCC 三坑**：幂等(条件更新)、空回滚(占位行)、悬挂(拒迟到 Try)。
- **`TccPeer`(application 声明) ↔ `HttpTccPeer`(infra 实现)**：出站端口——跨节点是"外部系统"，协调者只认语义不认传输。
- **FAILED vs CANCELLED 的口径**：问"有没有真的冻过钱"——没冻=FAILED，冻过又还=CANCELLED。
